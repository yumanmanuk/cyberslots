# Antigravity（agy CLI）切号方案 — 独立评审报告

> 评审对象：`docs/antigravity-integration.md`（下称"方案"）。
> 评审立场：怀疑的、找茬的。默认方案作者有确认偏误（方案自己做的、文档自己写的），本报告只输出批判与建议，不复述方案。
> 评审方法：通读方案全文 + 官方留档（`docs/antigravity cli v1.1.8/`）+ 本机实测留档（`.dev/workdir/` 脚本与输出）+ cockpit 账号库，交叉验证"文档声称"与"留档证据"是否一致。
> 评审维度：证据强度 / 工程健壮性 / 上下文续接 / 封号风险与合规伦理。

---

## 0. 总裁决

**有条件 go（引擎接入部分）/ no-go（13 号池自动轮换部分）。**

方案的技术调研质量是高的（stream-json 接口、权限模型、CLI/IDE 存储分离的逆向都扎实），但两个核心卖点——"无感切号已闭环"和"不丢上下文"——证据链都有致命断裂；封号风险评估则回避了决定风险量级的最大变量（账号来源）。

| 部分 | 裁决 | 前置条件 |
|---|---|---|
| 引擎接入（AntigravityAdapter + stream-json + 权限模型） | **有条件 go** | 补做三组实验：跨 client 注入 + 留档 401；时序攻击排除缓存；版本回归 |
| 手动切号（用户本人真实账号、低频故障转移） | **有条件 go** | 跑通跨账号续接裁决实验；结论改为诚实的"新对话+摘要重放"；落地互斥锁 + refresh_token 单一所有权 |
| 13 号池自动轮换 + 额度调度 + 错峰预热 | **no-go** | 价值主张与风险敞口是同一个东西，且混着疑似真实主号，不该进产品 |

## 1. 三个被多评审独立证实、且最致命的问题

### 致命①：两个最有分量的"实测铁证"在 `.dev/workdir/` 里没有任何留档

把 `.dev/workdir/` 全部脚本与留档文件 grep 一遍后：

- **"反证 401 UNAUTHENTICATED"**（§3.6）——零留档，只有文档口述。
- **"用 gemini-cli client 刷 keyring refresh_token 返回 401 unauthorized_client"**（§5，判定 client 归属的最强否定证据）——**零留档**。唯一有留档的 gemini-cli 刷新是刷 `oauth_creds.json` 的 refresh_token，结果是 **200 成功**（`quota-probe.txt`），与方案结论方向相反。
- 相比之下，403 PERMISSION_DENIED 是有 `quota-probe.txt` 留档的。

**含义**：方案把"有留档的 403"和"无留档的 401"并列为"实测铁证"，但后者的原始观测数据不存在。要么是没留档（补做即可），要么是记忆偏差（那 §5 的 client 归属结论要动摇）。**这两条必须从"铁证"降级为"待验证"，补做并留档。**

### 致命②：跨账号"不丢上下文"从未实测，且 §3.5 自己已经承认会失败

§3.6 的全部五行实测，验证手段都是 `agy -p`（单轮 headless **新会话**），判定标准是 `status:SUCCESS`。**没有任何一次实测验证过"切号后用旧 conversation_id 续接"**——`.dev/workdir/` 里不存在任何 conversation 续接测试脚本。

而 §3.5 原文写着"新账号后端可能无此会话→校验失败→新开"，§3.4 第 4 步写着"服务端新建对话可接受，符合需求"。**这两句已经承认了跨账号续接会失败、会新开。** 但 §0/§1/标题级结论反复用"不丢上下文"。

**含义**：会话是 Google 后端的计费/审计/隐私单元，几乎必然按账号隔离。跨账号 `--conversation <旧id>` 大概率校验失败、静默新开——即"不丢上下文"在跨账号时根本不成立，真实语义是"切号 = 新账号 + 新对话 + 上下文清零"。这直接抽掉了需求 §1 第一条的地基。更刺眼的是：官方留档 `resume.md` 的集成备注写了更诚实的版本（"无感切号更可能是新账号+新对话+重放上下文摘要"），**主文档反而把这句警告稀释掉了。**

**裁决实验（半小时，必须做）**：账号 A 跑 `agy -p "记住暗号 X，只回复 OK"` 拿 conversation_id → 切到账号 B → `agy -p "暗号是什么？" --conversation <A的id>`。看是答对（后端不绑账号）/ 答"不知道"且 id 变了（静默新开，证伪）/ ERROR（显式失败）。

### 致命③：13 个账号的来源问题被回避，本机证据指向批量获取，且混着疑似真实主号

核对 cockpit `accounts.json` 的 13 个账号后：

- **8 个账号的 `created_at` 集中在 2026-02-27 06:41:28–06:41:38，10 秒内连续导入 8 个**；另 3 个在同一天。正常用户不会 10 秒内拥有 8 个 Gmail。
- 命名模式：`enzoharris7777/7788/678`（同名人三号）、`1c6ot785`（随机字符邮箱）、`tuvantay111`（name 是键盘乱序 "Bbvy Fcguj"）——符合接码/账号商店产出特征。
- cockpit 内置 `wakeup_tasks.json`（每周一 07:00 唤醒全部 13 号）——"养号"是既定用法。
- **池子里混着 `yumanmanuk@gmail.com`，看起来是真实主号。**

**含义**：如果账号是购买/接码来的，§11.1"凭据层无风险（账号本人登录）"的前提垮塌——token 是真的，但账号本身是违反注册条款的产物。更关键的是**连坐风险**：Google 批量封禁通常按设备/IP/恢复信息连坐，`yumanmanuk` 这个疑似主号有被一起封的实际风险，§11 对此零警示。文档用"既有 cockpit 账号池、用户已自行承担的存量风险"一句话把来源问题滑过去了——**最需要盘问的前提被当成了既定事实。**

## 2. 证据强度（§3.1/§3.2/§3.6/§5）—— 不足以支撑结论

### 区分

- 【实测事实】rename `oauth_creds.json` 后单次 `agy -p` SUCCESS；切号 A/B 各一次 SUCCESS；写损坏凭据后一次 401。
- 【推断】由此推出"agy 每次调用实时读 keyring、无缓存兜底"。
- 【未验证假设】这个推断本身。

### 具体攻击

- **（致命）与官方文档直接冲突**：`installation-auth.md:25` 白纸黑字 *"Headless mode uses your **cached credentials**."* 方案引为地基的官方文档，用的词恰恰是它想排除的"cached"。方案所有实测都是"新进程单次单轮"，对"进程内/长会话/stream 中的缓存"零覆盖——**而 CyberSlots 恰恰要用 stream-json 长会话驱动，验证的场景和要用的场景不是同一个。**
- **（致命）两次切号 SUCCESS 是伪证**：样本量=2，且每次切号前 `build-switch-blob.mjs` 都用 enterprise client **预刷新了一次**。无法区分 agy 成功是"实时读 keyring"还是"被刷新动作预热"。缺"不预刷新、直接写过期 access_token 的 blob"的对照实验。
- **（高）`oauth_creds.json` 仍含活凭据且被还原**：quota-probe.txt 证明它的 refresh_token 刷 gemini-cli client 返回 200（有效）。§3.1 只证明"删掉它也能跑"（充分非必要），没排除 agy 在交互模式/刷新失败回退/特定模型下读它。
- **（高）id_token aud 只证单向**：aud=enterprise 只证明"这个 token 是 enterprise 签发的"，证明不了"agy 只接受 enterprise"。缺"跨 client 注入"实验（构造 gemini-cli client 的完整 blob 写进 keyring 看 agy 收不收）。
- **（高）blob 结构是单版本单样本快照**：1440B 是 token 长度的函数不是结构常量（§3.2 说 id_token len≈922，quota-probe.txt 里却是 1150，已自相矛盾）；UTF-8 判定用的是 `[Text.Encoding]::Unicode`（UTF-16LE）解码路径，本身可疑；版本漂移零覆盖。
- **（中）enterprise client secret 明文硬编码落盘**（`build-switch-blob.mjs:8`、`scripts/probe-agy-quota.mjs:33,36`），未进 git 是侥幸，方案 §11 大谈 TOS 风险却漏掉最基础的 secret 落地管理。
- **（中）"enterprise token 调额度端点 200"无直接留档**：§6.1 表格的"enterprise token ✅"那列只有 cockpit 链路间接证据，缺用 keyring 当前 token 直接调 `retrieveUserQuotaSummary` 的留档。
- **（低）反证临时文件残留**：`switch-email.txt` 当前内容是 `corrupted-negative-test@gmail.com`，`keyring-restore.ps1` 不清理反证临时文件，下次误跑会把损坏凭据写回 keyring。

## 3. 工程健壮性（§3.4/§3.6/§3.7/§8）—— 两个致命并发缺陷

- **（致命）两个 agy CLI 实例无法跑不同账号**：认证真源是全局唯一一条 keyring。§3.7 说"可 IDE 挂 A、CyberSlots 的 agy 同时跑 B"——这只证明了 CLI 和 IDE 两个**不同进程**能各挂一个号，**偷换概念**让人以为 CLI 内部能并行多账号。赛马并行场景下两个 agy 赛道必然共享同一 keyring 账号，中途切号会让在途 agy"半身换身份"。
- **（致命）refresh_token rotation 三方冲突**：同一个 refresh_token 被 cockpit（额度查询）、CyberSlots（切号构造）、agy（自动刷新）三条链路持有。Google refresh_token 会轮换，任何一方先刷都会让其他方手里的变成废票 → 下次 agy 自动刷新时 401 `invalid_grant`，表现为"切号成功但用着用着突然认证失效"，极难排查。§6.4 把"refresh_token 互通"当优点写，**这恰恰是最大的结构性风险源。**
- **（高）CredWrite + google_accounts.json 两步非原子**，keyring 无跨进程锁，与在途 agy 裸竞态。
- **（高）agy 刷新后是否写回 keyring 未验证**——无论写不写回，账号池的 blob 快照都会静默失效。
- **（中）blob 结构/条目名/client_id/路径全是 v1.1.8 私有实现**，升级即可能全断，无版本自检。
- **（中）google_accounts.json 被 agy 和 CyberSlots 双写竞争**。
- **（低）"反证"只证明无失败兜底，未证明运行中实时重读 keyring**——关键时序问题未钉死。

## 4. 上下文续接（§3.5/§6）—— 跨账号场景大概率不成立

见致命②。补充：

- **（高）方案内部自相矛盾**：§3.5 承认"校验失败→新开"，§1 却承诺"不丢上下文"。"新开空对话"和"不丢上下文"是两件事。
- **（高）即使小概率续接"成功"，恢复的只是对话文本**：system prompt / agent 配置 / 文件系统状态 / checkpoint 都不会跨进程恢复。任何续接实测必须用"只有旧上下文才有的信息"做探针，不能看退出码。
- **（中）自建"任务↔conversation_id"映射的键设计全文未说明**，同工作区多任务并发会撞键；映射表至少需 `(taskId, accountEmail, cwd) → conversationId` 三元组，并在切号时按 accountEmail 维度失效旧条目。
- **（中）`-c` 有三种出错模式**，其中"静默新开"最危险（失败不可见，自动化链路会把答非所问吞掉）。CyberSlots 应全面禁用 `-c`，只走显式 `--conversation`。
- **（低）会话后端保留期/TTL 完全未调研**，免费层会话几乎必有清理策略。

## 5. 封号/滥用风险（§11）—— 作者偏乐观，本评审判高（账号来源为购买/接码则极高）

### 不同意"官方CLI+真凭据显著降低被识别概率"

它消除的是伪造类信号（触发即时封禁），但 Google 对多号薅额度靠**关联聚类+批量复核**（慢变量）。§11 未盘点的硬信号：

1. **token 刷新时序指纹**（§11 完全没提，最强信号之一）：13 号 refresh 全部同一 IP、同一 client、秒级间隔，服务端原生日志，不受 UA 伪装影响。
2. **同一 enterprise client_id 是现成的 GROUP BY 键**：`SELECT DISTINCT user FROM oauth_log WHERE client_id='1071006060591-…' AND ip=X` 一条查询捞出全部 13 号。
3. **agy CLI 链路无指纹伪装**：cockpit 给每号配了独立 machine_id，agy 没有，CLI 侧"13 号同机"与 IDE 侧"13 号 13 机"双重矛盾。方案对"agy 是否上报机器标识"零验证。
4. **批量扫号查询额度本身就是最强的意图声明**：正常用户不会程序化周期查 13 个号的额度。

### 作者低估的关联向量

除上述，还有：账号命名/注册指纹（本机实证，见致命③）、恢复邮箱/手机号重叠、OAuth 授权时刻的浏览器 cookie/reCAPTCHA 历史信号（不可逆）。

### 风险形态

延迟的、批量的、连坐的——最容易被"跑了几个月都没事"麻痹。主号连坐风险 §11 零警示。

## 6. 合规与伦理 —— 分三层

- **引擎接入**（Adapter/stream-json/权限模型）：可以做，质量高。
- **单用户 2–3 个真实账号的手动故障转移**：灰色但可辩护。
- **13 号池 + 程序化轮换 + 额度调度 + 错峰预热：不该做，不该产品化。** 目的函数就是"额度利用率最大化 × N"，任何合理 TOS 解读下都是滥用。§11.4 的五条建议（留 buffer、加抖动、弱规律化）本质是反检测技巧——**为滥用目的降低可检测性是规避执法，比粗放滥用情节更重**，写进设计文档等于书面承认意图。一旦产品化，CyberSlots 从"用户自己玩火"变成"提供纵火工具"。

如果一定要做，最低边界：仅支持用户显式添加的账号、UI 明示"多账号轮换可能违反 Google ToS 并导致全部关联账号被封（含主号）"、不做自动轮换调度（只响应手动切换）、不做预热/养号、删除反检测建议章节。按这个边界，方案的卖点（无感轮换榨额度）也就所剩无几——**这恰恰说明方案的价值主张与其风险敞口是同一个东西。**

## 7. 替代方案 —— 比"覆写 keyring"更稳的做法

- **refresh_token 单一所有权**：账号池不缓存 blob 快照，切号总是现刷现写，写完后该号刷新权归 agy/CyberSlots 独占（不让 cockpit 再碰这些号的刷新）。
- **全局互斥锁**：agy 引擎全局单账号、赛道串行，切号必须 drain 所有在途 agy 进程后，用应用层互斥锁包住 CredWrite + google_accounts.json 两处写（写临时文件+原子 rename）。
- **降级为"手动切换 + 摘要重放"**：放弃自动轮换，只做用户手动触发的切号；上下文延续用应用层摘要重放（有损但诚实），不再假装能续接 conversation。
- **版本自检**：Adapter 启动时 CredRead 验证条目存在且 blob 能解析必需字段，否则拒绝切号告警；agy 版本钉在已验证范围。

## 9. 给方案作者的三句最直白的回应

1. 你说"实时读 keyring、无缓存兜底已坐实"——官方文档写的是"cached credentials"，你的实测全是新进程单次单轮，而你要用的是 stream-json 长会话。**你验证的场景和你要用的场景不是同一个。**

2. 你说"401 UNAUTHENTICATED 和 401 unauthorized_client 是实测铁证"——这两条在 `.dev/workdir/` 里**没有任何留档文件**，而方向相反的 200 和 403 却有留档。补做并留档，否则降级为"待验证"。

3. 你说"不丢上下文、无感切号已闭环"——你从未测过跨账号 `--conversation` 续接，§3.5 自己已经写了"校验失败→新开"。**半小时的暗号实验就能裁决，但在做之前，§1 的核心需求应降级为"切号后任务可继续（上下文经摘要重放有损保留）"。**
